## 0. 评审目标(本文通过的标准)

拿到一份输入材料和一个运行场景,只读本文及引用的契约,就能明确判断:**应该产生什么内容、留下什么状态、失败后如何继续**。不需要读者自行发明:候选何时固定、中断后从哪继续、人工操作影响哪些范围、零条目时维护者看到什么。

## 2. 内容字段与状态约定(两层样例的衔接契约)

功能与内容样例和页面呈现样例通过本表衔接:字段与状态先定死,页面只决定"怎么摆",不能引入本表之外的信息需求(要引入=先评审数据影响,见 §6)。

**期级(frontmatter,site 构建契约,spec §4.1 schema)**:

| 字段 | 类型 | 规则 |
|------|------|------|
| date | YYYY-MM-DD | 与文件名一致;运行开始时按 Asia/Shanghai 确定 |
| generated | true | 恒真 |
| ai_model | string | 本期实际调用模型;一期一模型(selection M1确定性边界) |
| entry_count | int | 正文条目数,修订后如实更新 |
| cost_cny | number | 发布时费用快照:该期全部 attempt 实付+未决保守预占,不重复计(pipeline 公开成本口径) |

**条目级**:

| 字段 | 归属 | 规则 |
|------|------|------|
| 中文标题 / 一句话摘要 / 推荐理由 | 读者可见 | understand 输出契约:标题≤30字答案先行、摘要一句话、理由不含来源未提的实体 |
| 原文链接 / 源名 / 展示分 / 板块 | 读者可见 | 链接必带;展示分=floor((score_1+score_2)/2);板块按展示分与源 tier 落位 |
| identity_key / url / published_utc / discovered_utc / source_tier | 系统内部 | spec §5.3 entry 表;判重键规则见 design.md |
| score_1 / score_2 / receipt 关联 | 系统内部 | analysis 表;跨期复用规则见 §4.5 |
| tags(≤3) | 系统内部 | **决策**:M1 只存 engine 侧,不进公开 markdown——digest schema 为 `.strict()`,展示需先扩 schema(挂 §6 待确认项),tag 本身服务 M2 RAG 语料 |

**期状态(引擎内部,digest_issue)**:无期记录 → draft → submitted → published;failed 为任一阶段的失败终态;撤回后 status 保持 published(发布是历史事实)+ 持久化撤回事实(暂停标志+撤回提交),当前可见性由站点内容决定(**决策**:不引入 withdrawn 状态值,避免"曾发布"与"当前可见"混在一个字段;存储映射属第 3 步)。

## 4. 一期生命周期

### 4.1 期状态机

```text
(无期记录)──collect 成功,候选冻结──▶(生成中,无期行)
    │                                   │评分/摘要,写 entry/analysis/receipt
    │ collect 失败                       ▼
    └──▶ failed(空 entry_ids)      组装出产物 ──▶ draft ──push──▶ submitted ──线上确认──▶ published
                                         │ 零合格/LLM 全挂               │push 冲突/超时(转人工窗口)
                                         └──▶ failed                     └─ 保持原状态,只重查
```

**决策(期行创建时机)**:`digest_issue` 行在首个终态性事件时创建——组装出产物(draft,带路径)或期内失败(failed);评分/摘要进行中没有期行,中断信息由 entry/analysis/receipt 承载(pipeline"无期记录"行的恢复依据)。DDL 不变。

### 4.2 阶段表(在 pipeline 阶段表之上补状态与冻结语义)

| 阶段 | 输入 | 输出与状态变化 | 失败去向 |
|------|------|----------------|----------|
| 0 定期 | 调度触发时刻 | issue_date=当时 Asia/Shanghai 日期(**补跑按补跑时刻定期,不回补停机各日**) | — |
| 1 collect | 上游只读,fetched_utc 近 48h | 候选写 entry 表;**窗口在此冻结**(§4.3) | E2 → failed(空),未冻结可重收集 |
| 2 预筛 | 冻结候选 | 剔除黑名单/死源/空正文/已 used/override exclude;按预算截断(公式见 design.md) | 本地零成本,无期级失败 |
| 3 双次评分 | 入围条目 | analysis(score_1/score_2);entry→scored;入选→selected | 额度停→带已有合格条目前进;单条失败跳过 |
| 4 摘要 | 入选条目 | 摘要 JSON;entry 保持 selected | 单条失败剔除该条,不挂期 |
| 5 组装 | 入选+摘要 | digest markdown 落工作副本;digest_issue=draft;零合格→failed(§3.5) | — |
| 6 发布 | 已验证产物 | push→submitted;线上确认→published;**entry→used 仅在确认 published 后** | E8/E9 → 产物保留,转人工窗口 |
| 7 汇总 | 全部 attempt | api_usage 投影、期成本快照 | 失败期同样记账 |

### 4.3 候选窗口冻结(缺口"窗口何时固定"的决策)

- **冻结点=本期第一次 collect 成功写入候选的瞬间。**此后该期一切续跑/补跑只使用已固定的候选集,不重新 collect 扩员——上游之后新抓取的内容不进入本期。
- 例外:该期在 collect 阶段即失败(零候选写入、零回执)→ 未冻结,重跑从头 collect,窗口=重跑时刻的近 48h。
- 功能判据:"该期是否已有候选写入或付费回执"。**候选集与期的归属如何存储(entry 加期归属列 vs 期行提前创建+候选快照)是第 3 步"数据接入与候选管理"单元的设计输入,本文不定存储**。
- 理由:中断续跑若重新 collect,48h 窗口滑移会改变候选集——已付费评分的条目可能掉出窗口、未评分的新条目混入,回执复用与费用一致性被破坏。冻结把"一次生成"变成对固定输入的可重放计算。

### 4.4 中断重跑:补跑 vs 重新生成(术语定稿)

| 术语 | 语义 | 触发 | 费用 | 候选集 |
|------|------|------|------|--------|
| **续跑(恢复)** | 同 issue_date 从库内状态继续:复用已收响应(按请求身份)、继续未完成阶段 | 任何中断后的下次调度或手动重跑(含 failed 期显式重跑) | 已付不重付 | 已冻结,不扩员 |
| **补跑** | 调度错过后的一次运行(systemd Persistent):按补跑时刻日期定期——该日无期数据=全新生成;已有未完成期=续跑。**停机多天只补一期,不回补每一天** | timer 补跑 | 同上 | 新期按补跑时刻窗口 |
| **重新生成** | 作废该期已有组装结果重走内容生成:**唯一入口是人工显式命令**。未发布期(draft/submitted):删旧产物、清组装结果、重新组装(能复用的响应仍复用);**已发布期不允许整期重新生成**,纠错走 §5.5 新提交 | 人工 | 复用照旧,新请求身份才新付费 | 已冻结,不扩员 |

各期状态下的具体恢复动作沿用 pipeline"期状态、断点与恢复"表(无期记录/draft/submitted/published/failed 五行),本文不复制;上表补的是三类运行的关系与候选/费用口径。

### 4.5 跨天、旧期与新期(缺口"跨天恢复/旧期阻塞"的决策)

- **调度顺序**:每次运行先续跑未完成旧期(推到终态或确认需人工),再处理当天新期;当天期已存在时,本次运行就是续跑它。
- **旧期不阻塞新期**:旧期停在需人工的状态(E8 冲突/E9 超时/暂停)时,当天新期照常生成。唯一全局阻塞是上游/数据库本身不可用(E2),当天期记 failed,不影响次日。
- **条目占用**:未发布期选中的条目不被其他待发布期占用(pipeline 既有规则);新期从剩余候选选。同一 identity_key 已有完整双次评分且 prompt 版本未变 → 跨期复用评分,不重复付费;prompt 变更后按新请求身份重评(旧 analysis 留档)。
- **未入选条目的自然淘汰**:rejected 条目次日仍可再入围(不因一次落选永拒);discovered_utc 滑出 48h 窗口即不再成为候选。M1 不设"落选冷却期"。
- **失败期的放弃**:failed 期由人工决定放弃时,核对后释放其占用条目(selected 回可评估状态,已 used 不动);操作留痕。不设自动放弃。

## 5. 人工维护流程(六场景)

统一约束:所有操作有命令或 Git 证据并留痕;已发生费用一律不退不改(账本是事实记录);对已发布内容的任何修改都走"新的已校验提交",不重写历史。

| # | 场景 | 触发与操作 | 生效范围 | 费用 | 文件 | 已发布内容 |
|---|------|------------|----------|------|------|------------|
| 5.1 | 排除条目 | override 写 `(identity_key, exclude, reason)` | 该 URL 的所有后续评估,即时生效 | 已付不退 | 当期未发布:移除该条并重新组装(其余条目摘要复用,零新增费用) | 不追溯;要改走 5.5 |
| 5.2 | 强制纳入 | override 写 `(identity_key, force_include, reason)`;条目须在冻结候选集中且有可核验正文 | 该 URL 存续期间的每次评估(当期+后续),可删除恢复纯评分判据 | 正常计费:强制项仍执行双次评分与摘要(展示分与账目一致) | 未发布期入选后参与组装 | 同 5.1 |
| 5.3 | 暂停一期 | 置期级暂停标志(命令,带原因) | 仅该期:调度直接跳过,不续跑不重发(W1);其他期与新期照常 | 无 | 冻结现状 | 冻结现状 |
| 5.4 | 恢复 | 显式解除暂停(留痕);此后按续跑语义 | 该期 | 复用照旧 | 续跑推进 | 若该期已 published 且被撤回:恢复=允许同日重建(见 5.6) |
| 5.5 | 纠错 | 专用工作副本修订该期 markdown → 本地 verify → commit+push → 线上确认;引擎补记纠错提交 | 仅该期内容;条目级错误同时写 5.1 防再犯 | 修订本身零模型费用;选择重写摘要=新请求身份、新费用归该期 | 该期文件更新,entry_count 如实变化 | 新版本替换旧版本,历史提交保留 |
| 5.6 | 撤回整期 | ①置暂停标志(防定时器重发)②删该期文件 → verify → push → 确认列表/详情/RSS 三处消失③引擎记录撤回事实(status 保持 published+撤回提交) | 整期下线 | 不退不改 | 文件删除(不做占位页,404) | 从站点消失;同日重建=解除暂停+显式重新生成(复用回执,§4.4) |

**强制项的统一纪律(决策)**:force_include 只越过评分门槛,不绕过来源/输入安全/预算约束(selection 既有);强制项**不静默降级也不静默丢弃**——超上限 15 或评分未完成(预算停)时,组装暂停并转人工处理,与 selection"有效强制项超上限时暂停组装"同一条规则。
