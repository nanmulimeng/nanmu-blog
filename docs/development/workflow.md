# Agent 开发工作流

> 本仓库由人和 agent 分会话协作开发。本文规定会话的固定动作,让任何会话产出可预期、可接续。纪律的来源:nanmuli-blog 死因之一就是跨会话断层(ADR-0008)。

## 会话开始(live_state 核对,必做)

1. 读根目录 `AGENTS.md` 与目标目录适用的局部规则。以本轮用户目标为准,旧 session 的 `next_action` 是建议,不能替代当前请求。
2. 读入口指向的最新 session,特别是 `objective`、`repository`、`omissions`。同日记录按 `recorded_at` 与 `continues` 判断接续,不按文件名字母排序。
3. 在仓库根分别执行以下只读命令,核对分支、已有修改、暂存区和提交。只对任务相关文件深入读 diff;不把工作区脏状态误判为需要清理。

```bash
git status --short
git diff --stat
git diff --cached --stat
git log --oneline -10
git branch --show-current
```

4. 实读相关实现、配置与计划步骤,记录本轮开始前已有改动的范围。初次接手补背景与 spec 总体边界;继续会话只补读本次影响的章节,不重复全量调研。
5. 按 [quality-gates.md](quality-gates.md) 的验证矩阵选择基线检查。尚无 `site/`、`engine/` 时不运行不存在的应用命令;文档任务不安装应用依赖或触发部署。
6. 交接与现场不符,先确定偏差来源并调整本轮执行依据。文件/运行证据描述实际状态,spec/ADR描述应有契约;实际偏离设计不代表设计自动失效。旧交接保留,纠偏写入新记录。

基线失败要区分既有缺陷、环境缺失和本轮引入的问题。与目标有关的缺陷先复现再修;无关缺陷记录影响并继续独立工作,不顺手扩大范围。未通过适用门禁的交付不能标为已验收;环境缺失也不能记成测试通过。

## 明确本轮范围与授权

开始修改前用简短说明明确:本轮要解决什么、预计影响哪些文件、用什么证据验收。普通文档或局部修复不要求另写计划文件。

| 情况 | 执行动作 |
|------|----------|
| 解释、只读审查、诊断 | 读取和报告;不因交接纪律主动写文件 |
| 已要求修改/修复,实现选择不改变目标和外部状态 | 直接做最小修改并验证,不重复索要已有授权 |
| 计划步骤因路径、命令或既有实现失效 | 核对实际消费方,修正计划后继续;不机械照抄 |
| 需要改变产品范围、核心约束或存在影响结果的歧义 | 先说明具体选择与影响,等待必要决定;继续不依赖决定的工作 |
| 提交、推送、上线、付费调用、不可逆操作 | 核对当前请求/已生效授权与精确目标;未获覆盖的操作先完成准备与验证,再请求该具体动作的确认 |

用户中途补充条件时并入当前目标;询问状态不等于取消任务。上下文切换后从已完成结果继续,不重复执行已确认的副作用。

## 保护工作区

- 已有修改和暂存默认属于用户或此前会话。不得通过 reset/restore/clean/stash 或覆盖整文件来取得“干净基线”;有重叠时读懂差异再最小合并。
- 修改公共名称、配置、schema 前搜索定义、引用与消费方;修改后复核。新增文件前先找可复用位置,避免多份真相源。
- 不因进入工作流就创建分支或提交。沿用当前合法工作分支;需要隔离时再建短期分支,不强切 main。
- 获准提交时逐文件/逐块检查并暂存本次范围,再读 `git diff --cached`;不用 `git add .` 混入未知修改。同一文件含此前改动且无法可靠拆分时,明确提交范围,不声称只提交了本轮工作。
- 临时脚本/夹具只写入已知临时目录;结束时只清理本轮明确创建的文件。删除前核对解析后的目标路径,不使用宽泛通配清理工作区。

## 任务执行

### 有 plan 时(默认情况)

- 按 plan 的依赖顺序执行;步骤实际完成且证据符合验收后再勾 checkbox。计划中的示例、mock通过或文档补全不能替代真实实施步骤。
- 按风险验证:逻辑缺陷/边界先复现失败再修复;静态文档、布局与脚手架用链接检查/build/产物核对。不要为流程形式制造无意义测试。
- **发现 plan 与现实冲突**:暂停受影响步骤,按上面的授权表处理。跨组件契约先改 spec/ADR,再同步计划与实现;纯路径勘误不要求新增 ADR。
- 必要的计划外修正记录原因、影响和验证;无关优化只记录候选,不扩展本轮范围。获准提交时保持逻辑变更独立,不为流程自动生成提交。

### 无 plan 时

- 小事(bug 修复、文档更新、局部调整):直接做,验证强度匹配风险。
- 大事(新功能、新子系统):先明确目标、约束和验收,再编写 spec/plan;需要用户决定的范围问题先对齐。流程不依赖某个 agent 产品或某个 skill 名称。

### 验证与失败处理

- 验证命令、工作目录和适用阶段统一见 [quality-gates.md](quality-gates.md);编码约束见 [coding-standards.md](coding-standards.md),不在此复制测试清单。
- 每次命令检查退出码与关键输出。长任务确认最终结束后才能记为通过,启动成功/返回进程 ID 不等于任务成功。
- shell 与运行环境先核对。Windows PowerShell、Git Bash 与服务器 shell 不混用语法;Git Bash 路径以本机实际值为准,避免把 WSL 启动器当成 Bash 环境。`.sh` 使用 LF。
- 有依赖的操作顺序执行,前置失败停止后续写入/提交/发布;独立只读检查可以并行。外部 IO 设置超时,失败单独记录,不吞掉核心错误。
- 同一修复方向连续两次无效,停止重复试错,汇总假设、已排除项与缺失证据,再选择下一步。缺工具时先找等价的可验证方式;替代检查覆盖不足则标明未验证,不伪造完成。
- 通过且之后未受相关修改影响的验证不重复。进度更新说明已确认结果、仍有的阻碍和下一步,不将预期输出写成实测结果。

### 提交规范

- 格式:`type(scope): 中文描述`或`type: 中文描述`(scope可选),type ∈ feat/fix/docs/chore/test/refactor/ops
- 一个逻辑变更一个 commit;TDD 的红/绿可以合为一个 commit
- **commit 前:对应层的自动验证必须绿**(这是硬门禁,见 [quality-gates.md](quality-gates.md))
- 项目通常在 main 小步提交,但不覆盖当前分支与已有工作;故障注入仅用独立临时验收仓库/目录,不得使生产 main 变红

### 依赖与密钥

- 新增运行时依赖:先判断 stdlib/现有依赖是否足够;不足则核对编码规范白名单与适用契约,记录引入理由,不凭工作流绕过约束
- **服务器密码仅交互输入;真实API key只进服务器环境**,由systemd `EnvironmentFile`提供;config/代码只有变量名引用。遵守[环境文档的凭据政策](../context/server-environment.md),本地单测用假值与mock;`.env`被gitignore不代表获准保存真实凭据

## 服务器任务

- Task8落盘工件并核对 `docs/ops/deploy.md` 后再按它与 ops/runbook.md 执行;命令与现场不符先修文档,不机械执行过期步骤
- 核对主机、目录、服务、remote和SHA;保护 topic-digest 与 nanmu-skill-mcp。历史环境记录不能代替当次现场检查。
- 验收关键输出(curl 状态码、脱敏日志摘要)记录进 session;不粘贴凭据或完整环境变量。命令与目标核对后按已有授权执行,超出授权的不可逆操作先列精确目标请求确认。
- 本地 build、Git commit、push成功、线上SHA确认是不同状态,分别记录;不能用其中一项代替其余项。

## 修改型会话结束(硬性步骤,不可省略)

1. 对最终改动运行适用验证;已通过且后续无相关改动的检查不重复,纯文档只记录文档检查结果
2. 写 `docs/sessions/YYYY-MM-DD-<主题>.md`(用 `_template.md`):state 带证据、omissions 显式列出
3. 更新 README/AGENTS/文档索引的最新交接入口与确实变化的状态快照;不改写历史 session。开发任务按授权提交 session;文档修改可留待统一提交,如实声明未提交
4. disposition 以**本轮 objective**为单位:complete=本轮承诺完成且适用验证有证据;continuable=尚有可继续的步骤;blocked=关键外部前提缺失且无法继续当前目标。文档完成不等于M0完成,待授权发布不能写已上线
5. 仅在已授权发布、目标remote核对正确、拟推送提交全部通过适用验证且无混入工作时,(M0 Task9后)执行`git push server main`;否则将未推送状态与原因写入omissions——服务器 bare repo 是相对开发机的代码副本,不等于 engine/rag 数据、凭据或服务器灾难恢复备份;未推送的提交只存在于开发机(nanmuli-blog 带着 601 行未提交工作死掉的教训)

被中断(上下文耗尽/用户打断)时同样适用——**宁可提前写 continuable 记录,不留断层**。

## 不确定时的顺序

查文档(spec/ADR/context)→ 查代码、配置与真实输出 → 需要外部事实时核对可靠来源 → 仍有影响目标的缺口再问用户。禁止凭猜测改代码或配置;禁止编造"文档里应该有"的内容。结束报告交付结果、实际验证、未验证边界和必要的下一步,不能只留下计划。
