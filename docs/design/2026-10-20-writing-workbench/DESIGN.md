# 文章管理工作台最小设计(2026-10-20,批次 C)

- **状态**:设计稿,待用户评审;**本批不实现**(2026-10-20 定点轮按用户 B1–B5 补齐契约)
- **范围(首版)**:浏览器内写作、草稿、预览、发布、撤下——单作者
- **不做(首版明示裁剪)**:多角色/多作者、评论、日报控制台、模型费用面板、通用 CMS 插件化、图片上传管理
- **方向(用户定)**:公开站保持静态,工作台独立;任何一层停运,公开博客照常在线

---

## 1. 为什么需要与总原则

现状:写作=开发机手写 Markdown → `git push`(origin 备份 + server 发布)。
缺口:离开开发机(或不想开终端)时无法安全地写作与发布;撤稿需要 Git 操作。

总原则:

1. **公开站零改动**:读者侧仍是 Caddy 服务的纯静态文件,无动态、无数据库、无会话。
2. **工作台是独立进程**:独立端口、独立认证、独立存储;崩溃/停运不影响公开站(铁律 2 的同型边界)。
3. **发布只走既有 Git 链路**:工作台不直接构建上线、不上传 dist、不改 hook——它做的只是「替作者执行一次受控的 git 提交与 push」,下游全部复用 [ADR-0007](../../decisions/0007-bare-repo-atomic-deploy.md) 的 bare repo + post-receive + 原子切版。
4. **AI 引擎隔离边界不动**:工作台不碰 engine 运行目录、timer、付费配置;二者互不感知。

## 2. 架构总览

```
作者 ──HTTPS──> 工作台服务(独立,子域 write.nanmu.xyz,Caddy 反代)
                  │  会话+口令(口令只在服务器 env)
                  │  草稿存储(工作台私有目录,不在 git 仓库内)
                  │  预览=临时 worktree 内跑与生产相同的 astro build
                  │
                  └─发布/撤下─> 工作台侧裸克隆 fetch+ff 校验
                                └─> push github main(备份,第 1 跳)
                                └─> push deploy main ──> 既有 hook 构建(第 2 跳)
                                      └─> releases/<SHA> 原子切 current
                                            └─> 轮询 /release.txt 判定上线

读者 ──HTTPS──> Caddy ──> current(静态文件)   ←与工作台零耦合
```

- **部署位置**:服务器上一个 systemd 服务(`nanmu-workbench.service`,监听 127.0.0.1:独立端口,Caddy 反代子域)。
- **备选(更小攻击面)**:仅 SSH 隧道访问、不暴露公网子域。首版推荐子域+口令(单作者日常便利),实施时可按用户裁决切换,两者代码相同。

### 2.1 Git 与远程:身份、worktree、凭据(定点轮 B1)

**Remote 一览(消除「origin 兼指两处」的歧义)**:

| remote 名 | 目标 | 读/写 | 职责 | 发布链中的位置 |
|---|---|---|---|---|
| `github` | `github.com:<user>/nanmu-blog`(GitHub 仓库) | 读写 | **仅备份**(历史与灾备);读者与部署均不依赖它 | 第 1 跳:push 成功才继续 |
| `deploy` | 服务器本地路径 `/opt/git/nanmu-blog.git`(bare,即既有发布裸仓) | 读写 | **唯一发布入口**:post-receive hook 构建与原子切版 | 第 2 跳:触发上线 |

工作台自建命名空间(其裸克隆里的 remote 名),与开发机互不影响;仓库真相源=deploy 指向的 bare(与现状一致,GitHub 是它的备份镜像)。

**提交发生在哪个 worktree**:不是「在裸克隆上提交」——bare 无法检出。工作台在服务器持有 `repo.git`(裸克隆,自 `/opt/git/nanmu-blog.git`)与一个**固定的发布 worktree** `/opt/nanmu-workbench/repo.wt`。每次发布:在 `repo.wt` 内 `fetch repo.git` → 将 main 快进到远端最新 → 应用本次变更(写入/删除文章 md)→ `git commit`(作者 `nanmu <workbench>`)→ push。worktree 复用(发布后不删,下次 fetch 快进),预览的临时 worktree(§4.3)另算、用完即删。

**GitHub 备份凭据**:SSH deploy key(仅本仓库写权限,服务器 `~/.ssh/` 私钥+GitHub 侧公钥),或等价的 Fine-grained PAT(Contents: RW,单仓库)。凭据只存在服务器文件系统标准位置(`~/.ssh/` 或 env),不进工作台代码、配置模板、日志与文档;丢失=服务器上重置(手册化)。

**部分成功状态与恢复(禁止任何 force push)**:

| 状态 | 含义 | 恢复动作 |
|---|---|---|
| 提交已生成,push github 失败 | 无远端影响 | 同一 commit 原地重试 push;仍失败→操作转「明确失败」,commit 保留在 worktree,草稿回到编辑 |
| github 已接收,push deploy 失败(网络/hook 拒绝) | 备份有,线上无 | **重试 push deploy 同一 SHA**(不重做 commit);hook 拒绝非 ff=按 §6 处理 |
| deploy 已接收,确认前进程中断 | hook 可能已构建 | 按 §4.4 恢复逻辑轮询 release.txt 判定,不重复 push |
| 180s 未确认 | 超出正常确认时间,**不等于失败** | 转入「暂未确认」持续后台轮询+可手动重查(§4.4) |

### 2.2 运行时与资源(定点轮 B5)

**选型(倾向,实施首批复核)**:

| 项 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node.js(与 site 构建同一运行时) | 服务器已为 site 构建装了 node;预览可直接复用同一套依赖 |
| Web 框架 | Fastify | 路由/中间件/日志开箱即用,依赖面小;Express/Koa 亦可,实施时定 |
| 口令哈希 | @node-rs/argon2(原生预编译);安装失败退 bcryptjs(纯 JS) | argon2id 是当前推荐;不引入手工编译原生模块的部署负担 |
| git 调用 | shell out 系统 `git` | 与 hook/CLI 行为一致,不经库二次实现;工作台只用本地路径 remote(§2.1),不涉凭据管道 |

**资源与争用(待测假设,不预设结论)**:

- 预览构建**并发上限 1**(单作者,排队即可);单次预览超时 120s,超时杀进程树并置失败态,构建错误原文返回作者。
- 与生产 hook 构建不并发(同一台服务器两个 astro build 会互相挤压内存):实施时核实 hook 侧互斥机制——若 hook 无现成锁,为 hook 与工作台共用一把构建锁文件;hook 构建进行中,预览排队等待并提示「部署构建进行中」。
- 原稿「空闲占用极低」「后续构建约 2-3s」两句是**未验证断言**,本轮降级为待测假设,实施验收按下列方法实测后回填,实测不达标则回到资源方案(降并发/串行化/加资源),不以停 AI 引擎为前提:
  - 空闲内存:服务上线后采样 24h(systemd `MemoryCurrent`,每 5min),报 P50/P95;
  - 预览构建耗时:真实草稿×20 次,报 P50/P95;
  - 预览构建窗口内的公开站影响:构建期间 GET 首页 20 次,报失败数与延迟。
- 工作台运行时只依赖 node+git+磁盘;不触碰 engine timer、topic-digest、付费配置(铁律 3/4/5 不变)。

## 3. 作者入口与认证

- 入口:`https://write.nanmu.xyz`(Caddy 反代;TLS 与主站同一套)。
- 认证:**单用户口令**。不以隐藏 URL 代替身份验证——URL 可被猜测/泄露,口令与 URL 独立。
  - 口令只存服务器 env 文件(`/opt/nanmu-workbench/env`,`WORKBENCH_PASSWORD_HASH=...`),凭据政策不变:不进任何文件/脚本/日志/文档。
  - 存储形态:慢哈希(argon2id 或 bcrypt);登录比对恒定时间。
  - 会话:HttpOnly+Secure+SameSite=Strict cookie,有效期 12h,过期重登;服务端会话表(内存+启动清理)。
  - 防爆破:登录失败限速(如 5 次/15min 锁定该来源 IP),登录尝试只记「失败次数与时间」,不记口令内容。
- CSRF(定点轮 B4):所有修改类 API(保存/发布/撤下/删除草稿)校验 `Origin`/`Referer` 恰为工作台子域,并要求自定义请求头(如 `X-Requested-With`)触发预检——跨站表单无法同时满足二者;GET 一律只读。
- 错误日志脱敏:不记口令、不记草稿正文;错误现场只留状态码、路径与异常类型。
- 无「记住我」、无找回口令(单作者:忘记口令=服务器上重置 env 后重启服务,操作写进运维手册)。

## 4. 操作路径(首版五操作)

### 4.1 列表
- 工作台首页=两张列表:**已发布**(读 git 仓库 main 上的 `site/src/content/posts/*.md`,显示标题/日期/字数)+ **草稿**(读草稿目录)。
- 每行动作:已发布→「撤下」「编辑(生成新草稿)」;草稿→「编辑」「预览」「发布」「删除草稿」。

### 4.2 新建/编辑
- 浏览器表单:标题、日期(默认今天)、tags(逗号分隔)、正文(Markdown 多行文本;首版纯文本域+等宽字体,不引入富文本编辑器)。
- 校验:文件名 slug(单层、小写英文数字短横线、非纯数字——复用 `site/src/lib/content.ts` 的 `assertPostsIds` 同规则,在工作台侧用同构校验,防发布时构建失败);标题非空;日期格式。

**编辑基准与外部修改检测(定点轮 B2)**:

- 每份草稿携带**编辑基准** `base`:`{commit: <SHA>, path: site/src/content/posts/<slug>.md, hash: <该文件内容 sha256>}`;从已发布文章「编辑(生成新草稿)」时写入,新草稿为 `null`。
- 发布前检测:fetch `deploy` 后读 bare main 上该 path 的内容 hash——与 `base.hash` 相同→可发布(正常路径);**同一文章被外部修改**(hash 不符)→拒绝发布,提示「这篇文章在发布裸仓上已被修改(另一窗口/开发机),请重新从列表生成草稿」,并给出两边首行差异预览;**无关文件变化**(其他文章/模板)→不阻塞,提交基准自动快进到新 main(§6 的 ff 链)。
- 并发保存(两个标签页同时编辑同一草稿):草稿每保存递增 `rev`(乐观锁);保存请求必须携带已知 `rev`,服务端不匹配→HTTP 409,前端提示「已在其他窗口保存,此处刷新后继续」,**绝不静默覆盖**;后写窗口的未保存内容展示在冲突提示里供手动取舍。
- **原子保存与中断恢复**:每次保存=写 `body.md.tmp` 与 `meta.json.tmp`(含新 rev)→按 body、meta 顺序同目录 rename(POSIX/NTFS rename 原子)→删旧 rev 副本。启动时若发现 tmp 残留(rename 中断)→丢弃 tmp,以 meta 的 rev 为准回退到上一完整 rev 并在界面标注「上次保存可能不完整,请检查」。编辑器本地(浏览器 localStorage)另存一份最近文本,冲突/中断后可一键找回。
- 持续输入的保存策略:输入停顿 30s 防抖自动保存+手动 ⌘S;**保存失败**(磁盘/进程错误)→状态条转红色「保存失败 HH:MM · 重试」,不再显示过期的「已保存」;有未保存更改时 `beforeunload` 弹离开确认(保存成功即解除)。

### 4.3 预览
- **复用实际渲染样式**:预览=真实构建,不是近似渲染。
- 实现:工作台在服务器上的裸克隆里开临时 worktree → 把草稿写入 `src/content/posts/` → 跑与生产相同的 `npm ci && npm run build` → 构建完成后**把整站产物拷贝到独立目录 `previews/<op-id>/` 并删除 worktree** → 从独立目录向作者返回预览。构建耗时是待测假设(§2.2),不预设秒数。
- 先例:与 `npm run verify` 的 fixture 临时构建同一模式,项目已验证可行。
- **鉴权与 URL 映射(定点轮 B4)**:`previews/` 是工作台私有目录(`/opt/nanmu-workbench/previews/`,Caddy 不服务它);预览 URL=`/preview/<op-id>/<path>`,整棵挂在会话中间件后——HTML 与 JS/CSS/字体等全部静态资源**同等鉴权**,不存在「页面要登录、资源不要」的缺口;由工作台进程流式读取独立目录返回。
- **存活期限与清理**:预览 24h 自动清理;同一草稿生成新预览时清掉它的旧预览。
- **删除 worktree 不影响打开中的预览**:worktree 只是构建脚手架,构建完拷贝产物即删;作者浏览器里打开的预览读的是独立副本,worktree 删除、乃至该草稿后续发布,都不使其失效,直至预览自身过期清理。
- 预览页带明显「草稿预览」横幅,且响应头 `X-Robots-Tag: noindex`(noindex 防索引,不是访问控制;访问控制=会话中间件)。
- **Markdown 原始 HTML/脚本/外部资源**:走与公开站完全相同的构建链路,首版不加 sanitize——信任源=作者本人(与作者手工 push md 完全等同,不新增信任对象);缓解=预览全量资源鉴权+独立子域(cookie `Domain=write.nanmu.xyz`)+公开站既有 ADR-0010 客户端 JS 白名单。见 §10 修正。
- **草稿不进公开产物的哨兵验收**:现有 smoke 的「drafts-example」检查只证明该夹具字串不出现,不证明任意草稿。补两层:每次预览构建自动在草稿正文注入随机哨兵串→对构建产物全量 grep,零命中才返回预览;实施验收另含「无会话直接 GET 预览 URL→401/302」「公开站 dist 全量 grep 哨兵零命中」(与本地 verify 的防泄漏检查同模式)。

### 4.4 发布
发布是异步过程,**提交成功≠上线成功**;且 **180s 未确认只代表超时,不代表失败**(定点轮 B3)。

**内部七态(持久化,界面收敛为五态显示)**:

| # | 内部态 | 含义 | 界面显示 |
|---|---|---|---|
| 1 | 已保存 | 草稿持久化在工作台 | 草稿中 |
| 2 | 提交已生成 | repo.wt 内 commit 已创建,push github 未返回 | 发布中 |
| 3 | 备份已接收 | push github 成功 | 发布中 |
| 4 | 部署端已接收 | push deploy 成功(返回成功≠已构建上线) | 发布中 |
| 5 | 确认上线 | release.txt == 本操作 commit SHA | 已上线 |
| 6 | 明确失败 | push 被拒/hook 非 ff 拒绝/构建失败等有明确失败信号 | 发布失败 |
| 7 | 暂未确认 | 180s 内未确认,**不判失败** | 未确认(后台持续轮询,可手动重查) |

**操作持久化与重启恢复**:每次发布/撤下创建一条 operation 并落盘(不只存内存):`{id: UUID, kind: publish|withdraw, slug, draft_rev, commit_sha, created/pushed_backup/pushed_deploy/confirmed/failed 时间戳, 终态}`。进程重启后对每条未终态操作按其 `commit_sha` 重放判定——SHA 已在 github main→态 3;已在 deploy bare main→态 4;release.txt == SHA→态 5;均无→回到对应态的恢复路径(见下表)。

**幂等与防重复提交**:操作身份=`operation id`+`commit SHA`。点发布后按钮立即置为进行中并禁用;前端响应丢失(断网)→按 id 查询状态,不重发提交;已有进行中的发布/撤下→拒绝并发提交,提示「上一次操作还在进行中」。

**列表「已上线」的判定口径**:不以「git 仓库里存在该文章 md」为准(那只证明提交过,不证明上线过)。已上线=GET `https://nanmu.xyz/posts/<slug>/` 为 200(撤下=404),配合 release.txt 维护「上次确认上线的 SHA」;列表徽标由该口径驱动。

流程:发布按钮(二次确认:显示标题/slug/是否含撤下项)→ 创建 operation → repo.wt fetch+ff 校验(§6)→ 草稿转正式 md(`draft` 字段省缺=false)→ commit(署名 `nanmu <workbench>`,message `post(site): 发布〈标题〉`)→ push github main(态 2→3)→ push deploy main(态 3→4)→ 后台轮询 release.txt(180s 口径)→ 达标转态 5,草稿移入「已发布」;明确失败信号转态 6 并保留草稿;仅超时转态 7。

**五中断场景推演(态 7 或进程中断的恢复路径)**:

| 中断点 | 现场证据 | 恢复动作 |
|---|---|---|
| 推送 github 前 | commit 只在 repo.wt | 重试 push 同一 commit(不重做) |
| github 已接收,deploy 未接收 | github main == SHA,deploy main != SHA | 重试 push deploy 同一 SHA(不重做 commit) |
| deploy 已接收,确认前进程中断 | deploy main == SHA,release.txt 未知 | 不重复 push,按重放逻辑轮询 release.txt |
| 实际已上线但未补记确认 | release.txt == SHA | 重放判定直接补记「已上线」 |
| 后续版本已上线(本操作被包含) | release.txt 为更新 SHA,但其祖先链含本 SHA | 判「已被后续版本包含」→按已上线处理;撤下类操作以 GET 文章 URL 404 终验 |

### 4.5 撤下
- 与发布同链路:工作台 `git rm` 该文章 md → commit(`post(site): 撤下〈标题〉`)→ push(同上状态机)。
- 撤下确认页明示影响面(从批次 C 撤稿经验固化):正文 URL 将 404、列表/首页/RSS/3D 纸面不再出现;**回滚到含该文的旧 release 会重新公开它**(若该 release 仍在保留窗口)。
- 撤下不改写 Git 历史(与既有纪律一致);旧文在 git 历史中保留。

## 5. 草稿:存哪、谁能读、如何不误进公开页

- **存储**:工作台私有目录 `/opt/nanmu-workbench/drafts/`(一草稿一目录:`<slug>/meta.json` + `<slug>/body.md`)。**不在 git 仓库内、不在 site 构建源内、不被 Caddy 服务**。
- **谁能读**:仅通过 §3 认证的作者会话;草稿 API 全部挂在会话中间件后,无公开路由。
- **防误公开三道闸**:
  1. 物理隔离:草稿目录与发布仓库分离;公开构建(`astro build`)只读 `site/src/content/posts/`,草稿不在其内——构建器不知道草稿存在。
  2. 显式转换:草稿→公开文章必须经「发布」动作(生成 md + commit + push),不存在自动收录路径;frontmatter `draft:true` 字段保留为纵深防御(误放源目录时构建期仍过滤,与既有 smoke「草稿泄漏」检查双层兜底)。
  3. 输出侧校验:hook 构建后的 smoke(既有)断言必需产物与草稿不泄漏;工作台发布后自行 GET 文章 URL 确认 200(或撤下后 404)作为终验。
- 草稿备份:纳入服务器每日备份(与 engine SQLite 同批;具体策略实施时定)。

## 6. 与 Git 手工编辑并发:防覆盖

- 工作台在服务器持有**裸克隆** `repo.git`(自 deploy 即 `/opt/git/nanmu-blog.git` 克隆,§2.1);每次发布/撤下前:
  1. `git fetch deploy` 更新引用(deploy=唯一发布真相源;github 只是备份,不作为 fetch 对象);
  2. 基于最新 main 创建短期分支做提交;
  3. push 前检查目标 main 未前进(即推送为 fast-forward)。**非 ff=并发编辑发生**(典型:作者同时在开发机 push),工作台拒绝发布并提示「远端有新提交,已回到编辑,请重新预览/发布」,**绝不 force push**(与既有部署纪律一致)。
- 手工编辑侧无需感知工作台:git 是唯一真相源,两边最终以 bare repo 收敛。

## 7. 故障与降级

| 故障 | 影响 | 行为 |
|---|---|---|
| 工作台进程崩溃/停机 | 仅写作能力不可用 | 公开站照常(Caddy→静态文件,不经工作台);systemd 自动重启;草稿在磁盘不丢 |
| 发布中 hook 构建失败 | 发布失败,线上仍是旧版 | 原子切版保证;hook 侧**明确失败信号**→「发布失败」提示人工查看(不自动回滚、不自动重试);仅 180s 无确认→「暂未确认」持续轮询(§4.4),不与失败混同 |
| 预览构建失败 | 预览不可用 | 返回构建错误原文(作者可修);不影响任何已发布内容 |
| 口令遗忘 | 无法登录 | 服务器重置 env(手册化操作),不设找回流程 |

## 8. 对既有约束的调整(需新 ADR,实施第 1 步)

- **ADR-0002(静态站无后台)**:原约束语义=「公开站不给读者任何动态面、git 即 CMS」。调整=精确分面:
  - 公开站(读者侧)**不变**:仍无后台、无数据库、无会话,客户端 JS 白名单(ADR-0010)不变——工作台页面不混入公开站构建产物。
  - 新增**作者私有工作台**:独立进程/端口/认证/存储,不触碰公开站静态性质;它发布内容的唯一出口是 git commit+push(与作者手工操作完全同权同路)。
  - 实施时立 ADR-0011 记录此修订;ADR-0002 正文加一行指向。
- **铁律不变清单**:博客本体不为 AI 加复杂度(工作台属博客本体自身的作者工具,不涉 AI);engine 隔离(铁律 3)不涉;topic-digest 只读(铁律 4)不涉;付费红线(铁律 5)不涉;页面不调模型(铁律 6)不涉;AI 标注(铁律 7)不涉;文档随代码走(铁律 8)照常。
- **部署边界新增**:工作台是新的服务器组件,其 systemd/Caddy 反代/env 属新增配置,实施时按部署手册流程走授权;不改既有 hook、不改 Caddy 主站配置文件既有段(只加子域反代段)。

## 9. 实施分解建议(后续批次,另行计划)

1. ADR-0011 + 运维手册增补(子域/env/systemd);
2. 工作台服务骨架(认证+会话+草稿 CRUD);
3. 预览(临时 worktree 构建);
4. 发布/撤下状态机(裸克隆+ff 校验+release.txt 轮询);
5. 验收专项用例:「工作台停运公开站照常」「非 ff 拒绝」「草稿不进公开构建(随机哨兵,非固定夹具串)」「发布失败与暂未确认两态区分」「预览 URL 无会话 401/302」「§2.2 资源三项实测(空闲内存/预览耗时/构建窗口公开站影响)回填设计」。

## 10. 安全清单(实施对照)

- 口令仅 env 慢哈希;登录限速;会话 cookie 三标记;失败日志不含口令。
- 草稿/预览/发布 API 全部会话后;预览 noindex;无公开枚举接口。
- git 操作只用裸克隆本地路径,不引入远程凭据;bare repo 权限沿用部署手册。
- 不上传任意文件(仅 md 文本字段)。Markdown 渲染发生在构建期、与公开站同一渲染器——**但「渲染器相同」只降低差异风险,不构成「无新增注入面」的结论**(定点轮 B4 删去原句):信任源=作者本人(与手工 push 等同,不新增信任对象),缓解=预览全量资源鉴权(§4.3)+子域隔离+ADR-0010 白名单;草稿携带原始 HTML 的实际放行范围以实施时哨兵验收与专项用例实测后再定。
