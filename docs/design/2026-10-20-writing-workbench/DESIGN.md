## 1. 为什么需要与总原则

现状:写作=开发机手写 Markdown → `git push`(origin 备份 + server 发布)。
缺口:离开开发机(或不想开终端)时无法安全地写作与发布;撤稿需要 Git 操作。

总原则:

1. **公开站零改动**:读者侧仍是 Caddy 服务的纯静态文件,无动态、无数据库、无会话。
2. **工作台是独立进程**:独立端口、独立认证、独立存储;崩溃/停运不影响公开站(铁律 2 的同型边界)。
3. **发布只走既有 Git 链路**:工作台不直接构建上线、不上传 dist、不改 hook——它做的只是「替作者执行一次受控的 git 提交与 push」,下游全部复用 [ADR-0007](../../decisions/0007-bare-repo-atomic-deploy.md) 的 bare repo + post-receive + 原子切版。
4. **AI 引擎隔离边界不动**:工作台不碰 engine 运行目录、timer、付费配置;二者互不感知。

## 2. 架构总览

```
作者 ──HTTPS──> 工作台服务(独立,子域 write.nanmu.xyz,Caddy 反代)
                  │  会话+口令(口令只在服务器 env)
                  │  草稿存储(工作台私有目录,不在 git 仓库内)
                  │  预览=临时 worktree 内跑与生产相同的 astro build
                  │
                  └─发布/撤下─> 工作台侧裸克隆 fetch+ff 校验
                                └─> push github main(备份,第 1 跳)
                                └─> push deploy main ──> 既有 hook 构建(第 2 跳)
                                      └─> releases/<SHA> 原子切 current
                                            └─> 轮询 /release.txt 判定上线

读者 ──HTTPS──> Caddy ──> current(静态文件)   ←与工作台零耦合
```

- **部署位置**:服务器上一个 systemd 服务(`nanmu-workbench.service`,监听 127.0.0.1:独立端口,Caddy 反代子域)。
- **备选(更小攻击面)**:仅 SSH 隧道访问、不暴露公网子域。首版推荐子域+口令(单作者日常便利),实施时可按用户裁决切换,两者代码相同。

### 2.1 Git 与远程:身份、worktree、凭据(定点轮 B1)

**Remote 一览(消除「origin 兼指两处」的歧义)**:

| remote 名 | 目标 | 读/写 | 职责 | 发布链中的位置 |
|---|---|---|---|---|
| `github` | `github.com:<user>/nanmu-blog`(GitHub 仓库) | 读写 | **仅备份**(历史与灾备);读者与部署均不依赖它 | 第 1 跳:push 成功才继续 |
| `deploy` | 服务器本地路径 `/opt/git/nanmu-blog.git`(bare,即既有发布裸仓) | 读写 | **唯一发布入口**:post-receive hook 构建与原子切版 | 第 2 跳:触发上线 |

工作台自建命名空间(其裸克隆里的 remote 名),与开发机互不影响;仓库真相源=deploy 指向的 bare(与现状一致,GitHub 是它的备份镜像)。

**提交身份:复用物理 worktree,隔离每次操作(定点轮 B3 修订)**:不是「在裸克隆上提交」——bare 无法检出。服务器持有 `repo.git`(裸克隆)与**固定的发布 worktree** `/opt/nanmu-workbench/repo.wt`(物理复用,不重建)。**每次发布/撤下=一个短期操作分支 `op/<op-id>`**:repo.wt 内 fetch → main 快进到 deploy 最新 → 自该 main 检出 `op/<op-id>` → 应用本次变更(写入/删除文章 md)→ `git commit`(作者 `nanmu <workbench>`)→ push。操作成功(main 已接收)后 main 快进到该提交并**删除操作分支**;**操作失败或取消→保留 `op/<op-id>` 分支作为恢复证据,repo.wt 立即检出回 main**——下一次操作从最新 main 新建自己的分支,失败提交绝不作为后续发布的默认父提交。预览的临时 worktree(§4.3)另算、用完即删。

**GitHub 备份凭据**:SSH deploy key(仅本仓库写权限,服务器 `~/.ssh/` 私钥+GitHub 侧公钥),或等价的 Fine-grained PAT(Contents: RW,单仓库)。凭据只存在服务器文件系统标准位置(`~/.ssh/` 或 env),不进工作台代码、配置模板、日志与文档;丢失=服务器上重置(手册化)。

**GitHub 与 deploy 两端不一致(常态,不是错误;部分成功未决时阻止新发布,不自动收敛)**:既有实践存在「纯文档提交推了 GitHub、未推 server」的正常状态,工作台不假设两端同步;但**绝不用「新操作顺路快进」把未决内容自动带往 deploy**(定点轮收口:删除原「github 领先→操作分支快进后双推收敛」规则——它正是内容夹带的通道)。收敛只允许 deploy→github 方向(备份追上真相源,安全);github→deploy 方向的任何领先都不自动带。

- **时序**:①**创建新 operation 时**一次性 fetch deploy 与 fetch github,记下两端 main SHA 作为本次基准;②此后分支/提交/推送均基于该基准,不中途重读、不中途合并;③检出 `op/<op-id>`(基准=deploy main)→ commit → 双跳 push。
- **新 operation 的创建闸门(全部满足才开)**:(a) 无未终态 operation(进行中/部分成功/暂未确认都算未终态)——有→拒绝新发布,提示「操作 X 尚未解决,先按 §2.1 恢复表处理」;(b) github main == deploy main,或 github main 是 deploy main 的祖先(落后)——github **领先**或**分叉**→停止并列出差异提交**转人工**,不强推、不自动合并、不引入分支管理平台。人工处理方式按部署手册(如人工使两端一致或明确暂缓),工作台不代做决定。
- **允许继续同一 operation 的事实**(按既有身份恢复,不新建提交):github main == 本 op 的 commit_sha→只重试 push deploy 同一 SHA;deploy main == commit_sha→进入确认轮询;两端均不含该 SHA 且 `op/<op-id>` 分支 HEAD==该提交→重试双跳;分支 HEAD==基准(未提交)→重做提交。
- **取消本地操作 ≠ 撤销已推送提交**:界面取消只放弃本地继续;已 push github(或 deploy)的提交仍在远端——取消时如实提示「已推送的提交保留在远端,需人工决定是否处理」,工作台不删远端提交、不假设取消=回滚;该 op 终态记「已取消(远端残留注明)」。
- **新操作不继承未决内容**:每次基准=当时 deploy main;未决 op 的提交未到 deploy,天然不在后续基准内;闸门(a)(b) 保证不存在「带着未确认内容发布」的路径。

**部分成功状态与恢复(禁止任何 force push;解决前新发布被闸门阻止)**:

| 状态 | 含义 | 恢复动作 |
|---|---|---|
| 提交已生成,push github 失败 | 无远端影响 | 同一 commit 原地重试 push;仍失败→操作转「明确失败」,提交保留在 `op/<op-id>` 分支,repo.wt 检出回 main,草稿回到编辑 |
| github 已接收,push deploy 失败(网络/hook 拒绝) | 备份有,线上无 | **重试 push deploy 同一 SHA**(不重做 commit);hook 拒绝非 ff=按 §6 处理;未解决期间新发布被闸门阻止 |
| deploy 已接收,确认前进程中断 | hook 可能已构建 | 按 §4.4 恢复逻辑轮询+内容身份核对判定,不重复 push |
| 180s 未确认 | 超出正常确认时间,**不等于失败** | 转入「暂未确认」持续后台轮询+可手动重查(§4.4);终态化前新发布被闸门阻止 |

**B3 反例验收(五场景,收口轮重写)**:

| 反例 | 预期 |
|---|---|
| 1. A 部分成功(github 有 A、deploy 无)后开始 B | 闸门(a)拒绝 B;不自动把 A 带到 deploy;先恢复 A 或人工终态化 |
| 2. A 同 operation 重试 | 识别 github main==A 的 SHA→只重试 push deploy 同一提交,不新建 commit/operation |
| 3. 用户取消 A | 本地放弃;已推远端的提交保留并如实提示人工处理;A 终态「已取消(远端残留注明)」,此后闸门(a)解除、闸门(b)仍按远端实况判定 |
| 4. 无关提交(如手工文档提交)使 github 领先 deploy | 新 operation 创建时闸门(b)检测到→停止+差异提交列表转人工,不自动收敛 |
| 5. 真实分叉(两端互不为祖先) | 同闸门(b)→转人工,不强推、不自动合并 |
| 6. 新草稿保存期间同 slug 文章被手工创建 | 发布前 slug 占用检查(§4.2)拒绝覆盖,提示改 slug |

**资源与争用(待测假设,不预设结论)**:

  - 空闲内存:服务上线后采样 24h(systemd `MemoryCurrent`,每 5min),报 P50/P95;
  - 预览构建耗时:真实草稿×20 次,报 P50/P95;
  - 预览构建窗口内的公开站影响:构建期间 GET 首页 20 次,报失败数与延迟。
- 工作台运行时只依赖 node+git+磁盘;不触碰 engine timer、topic-digest、付费配置(铁律 3/4/5 不变)。

## 3. 作者入口与认证

- 入口:`https://write.nanmu.xyz`(Caddy 反代;TLS 与主站同一套)。
- 认证:**单用户口令**。不以隐藏 URL 代替身份验证——URL 可被猜测/泄露,口令与 URL 独立。
  - 口令只存服务器 env 文件(`/opt/nanmu-workbench/env`,`WORKBENCH_PASSWORD_HASH=...`),凭据政策不变:不进任何文件/脚本/日志/文档。
  - 存储形态:慢哈希(argon2id 或 bcrypt);登录比对恒定时间。
  - 会话:HttpOnly+Secure+SameSite=Strict cookie,有效期 12h,过期重登;服务端会话表(内存+启动清理)。
  - 防爆破:登录失败限速(如 5 次/15min 锁定该来源 IP),登录尝试只记「失败次数与时间」,不记口令内容。
- CSRF(定点轮 B4;勘误轮补服务端校验):所有修改类 API(保存/发布/撤下/删除草稿)校验 `Origin`/`Referer` 恰为工作台子域,并要求自定义请求头(如 `X-Requested-With`)触发预检——跨站表单无法同时满足二者;GET 一律只读。**服务端处理器对 Origin 与自定义头做实际校验(缺失/null Origin/不匹配即 403),不以浏览器预检为唯一机制**——直连 HTTP 不经预检,探针 v2 以四路直连(无会话/伪造 Origin/null Origin/缺自定义头)实测全部拒绝且数据未变。
- 错误日志脱敏:不记口令、不记草稿正文;错误现场只留状态码、路径与异常类型。
- 无「记住我」、无找回口令(单作者:忘记口令=服务器上重置 env 后重启服务,操作写进运维手册)。

## 4. 操作路径(首版五操作)

### 4.1 列表
- 工作台首页=两张列表:**已发布**(读 git 仓库 main 上的 `site/src/content/posts/*.md`,显示标题/日期/字数)+ **草稿**(读草稿目录)。
- 每行动作:已发布→「撤下」「编辑(生成新草稿)」;草稿→「编辑」「预览」「发布」「删除草稿」。

### 4.2 新建/编辑
- 浏览器表单:标题、日期(默认今天)、tags(逗号分隔)、正文(Markdown 多行文本;首版纯文本域+等宽字体,不引入富文本编辑器)。
- 校验:文件名 slug(单层、小写英文数字短横线、非纯数字——复用 `site/src/lib/content.ts` 的 `assertPostsIds` 同规则,在工作台侧用同构校验,防发布时构建失败);标题非空;日期格式。

**编辑基准与外部修改检测(定点轮 B2)**:

- 每份草稿携带**编辑基准** `base`:`{commit: <SHA>, path: site/src/content/posts/<slug>.md, hash: <该文件内容 sha256>}`;从已发布文章「编辑(生成新草稿)」时写入,新草稿为 `null`。
- 发布前检测:fetch `deploy` 后读 bare main 上该 path 的内容 hash——与 `base.hash` 相同→可发布(正常路径);**同一文章被外部修改**(hash 不符)→拒绝发布,提示「这篇文章在发布裸仓上已被修改(另一窗口/开发机),请重新从列表生成草稿」,并给出两边首行差异预览;**无关文件变化**(其他文章/模板)→不阻塞,操作基准取最新 main(§6 的 ff 链)。
- **新建草稿(base=null)同样做 slug 占用检查**(定点轮 B3 补):发布前 bare main 上 `posts/<slug>.md` 已存在→拒绝发布并提示改 slug,绝不允许覆盖他人/先前创建的同名文章;保存草稿时即预检一次并提示(最终闸门仍在发布前)。

**保存提交点(定点轮 B1 重写:单记录一次替换)**:

- **存储结构:一份草稿=一个记录文件** `<slug>/draft.json`,同时含正文、元数据与 `rev`(不再拆 body.md/meta.json 两文件)。保存=把完整新记录写 `draft.json.tmp` → `fsync(tmp)` → **一次 `rename(tmp → draft.json)`**——这次替换是唯一的保存提交点。
- 上一版保留:替换成功后把被替换下的旧记录存为 `<slug>/draft.prev.json`(仅一份,下次保存覆盖);它只用于「当前记录损坏」的兜底恢复,不是版本历史。
- **rev 检查与写入不可被插入**:服务端对每份草稿维护单写者串行队列——同一草稿的保存请求排队处理,处理中=「读 rev → 校验请求 rev → 写 tmp → rename」整体持有该队列;两个窗口携带同一 rev 同时保存,只有第一个成功(rev+1),第二个收到 409「已在另一窗口保存」,前端提示「此处刷新后继续」,后写窗口的未保存内容展示在冲突提示里供手动取舍,**绝不静默覆盖**。
- **「保存成功」的返回时机**:rename 完成之后。rename 之前任何时刻的响应都不声称已保存;rename 后进程崩溃而响应未送达→客户端视为失败并重试,重试携带旧 rev→409→刷新即见已保存内容(内容没丢,只是状态误报一次)。
- **中断恢复(只允许完整旧版或完整新版)**:启动/每次读取时,`draft.json` 永远是最后一次成功 rename 的完整记录——tmp 残留=替换未发生→丢弃 tmp,当前版即旧版;`draft.json` 解析失败(极端)→回退 `draft.prev.json` 并在界面标注「已恢复到上一完整保存,请检查」。正文与元数据同文件同 rev,结构上不存在「新正文+旧元数据」混搭。
- **持久化保证边界(明示)**:以上保证的是**进程崩溃/正常重启**的恢复。掉电/OS 崩溃:tmp 写入后 fsync、rename 后 fsync 目录,已把窗口压到最小,但**不承诺跨掉电零丢失**——按同一恢复规则处理(丢的是最后一次未完成替换,最多回到上一次提交点)。
- **持续输入的保存上限**:停顿 30s 防抖之外,**最长 60s 周期保存**(持续输入也每 60s 落盘一次)+手动 ⌘S;界面常显「已保存 HH:MM(rev N)」与未保存变更标记。
- **浏览器本地副本(补救位,不属保存契约)**:输入时节流 2s 写 localStorage;**服务端保存成功即清空**;仅当打开草稿时发现 localStorage 有比服务端新的文本,提示「本地有未保存内容,恢复?」;保留政策=只留最近一次会话的未保存文本,用户确认丢弃或恢复后删除。它救的是「忘点保存关了页」,不参与 rev/并发/原子性契约。
- 保存失败(磁盘/进程错误)→状态条转红色「保存失败 HH:MM · 重试」,不显示过期的「已保存」;有未保存更改时 `beforeunload` 弹离开确认(保存成功即解除)。

**B1 反例验收(四条)**:

| 反例 | 预期 |
|---|---|
| 1. tmp 写完但未替换时中断 | 重启后 draft.json 仍为旧完整版,tmp 被丢弃;界面无「已保存」假象 |
| 2. 提交点附近中断,重启 | draft.json 为完整新版且正文与 rev 一致(或完整旧版),绝不出现半新半旧 |
| 3. 两标签页携同一 rev 同时保存 | 恰一个 200(rev+1),另一个 409;无双重写入 |
| 4. 连续输入超过保存周期 | 每 ≤60s 落盘一次,状态条能明确指出「已保存到哪一版」与「其后有多少未保存变更」 |

### 4.3 预览
- **复用实际渲染样式**:预览=真实构建,不是近似渲染。
- 实现:工作台在服务器上的裸克隆里开临时 worktree → 把草稿写入 `src/content/posts/` → 跑与生产相同的 `npm ci && npm run build` → 构建完成后**把整站产物拷贝到独立目录 `previews/<op-id>/` 并删除 worktree** → 从独立目录向作者返回预览。构建耗时是待测假设(§2.2),不预设秒数。
- 先例:与 `npm run verify` 的 fixture 临时构建同一模式,项目已验证可行。

**鉴权、同源与资源映射(定点轮 B2 修订)**:

- `previews/` 是工作台私有目录(`/opt/nanmu-workbench/previews/`,Caddy 不服务它);预览 URL=`/preview/<op-id>/<path>` 由工作台进程流式读取返回。**资源鉴权两层(勘误轮定案)**:「整棵挂会话中间件」不可行——opaque origin 文档发起的子资源请求(CSS/字体/图片)**不携带会话 cookie**,会把它们全部变成 401(这正是 v1 探针 fonts.css 401 的机制)。定案:预览 HTML(导航请求,带 cookie)按会话鉴权;子资源改由**短期资源 token** 鉴权。
- **资源 token 的性质与边界(首版收敛轮定案,不建设通用授权框架)**:性质=**短期 bearer 资源凭证**——绑定会话仅用于撤销与有效性检查(会话失效→凭证连带失效),不要求子资源请求携带登录 cookie。记录与校验的最小范围只有四项:**所属会话、所属预览 ID、有效期(30 分钟)、允许的子资源类别(css/font/img)**。HTML 永远只走登录访问路径,**管理 API 永不接受资源 token**。凭证校验:未过期+会话活跃+**预览仍存活**+凭证所属预览=请求的预览+资源类别在允许范围内,任一不满足即 401(预览已删除/到期→410);**预览的 24h 保留期与凭证的 30 分钟有效期是两个独立生命周期**——预览被删除或到期后,未过期凭证同样失效;从有效会话重新打开保留期内的预览会获得新凭证(旧凭证不因重开而延长);服务端日志只记路径不记 query(token 值不进日志与交接);不承诺撤回已下载到浏览器的资源。工作台返回预览 HTML 时签发 token 并注入资源 URL(`?t=`),CSS 内容内的分片 URL 由服务端改写补同一 token;响应头 `Referrer-Policy: no-referrer`(token 不随 Referer 外泄)。公开静态字体分片响应带 `Access-Control-Allow-Origin: *`——字体加载走 CORS 模式,opaque origin 视为跨源,无 ACAO 时**网络层 200 的响应仍被字体层拒绝**、FontFace 停留 unloaded(本地探针实测);ACAO 只作用于公开静态字体文件,不涉草稿内容。
- **同源事实(不再称「预览与管理已通过子域隔离」)**:预览与管理界面**同在 write.nanmu.xyz,同源,二者之间没有隔离**;真正隔离的是 write.nanmu.xyz 与公开站 nanmu.xyz(不同 site,cookie/脚本互不可达)。同源意味着预览页面里的脚本若放任执行,就与管理工作台共享站点上下文——这是下面活动内容策略的直接原因。
- **根路径资源映射**:公开站页面引用根路径(/fonts/fonts.css、/scripts/site.js、/3d/…、/favicon.svg),把整站文件放到 `/preview/<id>/` 下**不会自动改写这些请求**。方案=**构建后前缀改写**:预览构建完成后,把产物 HTML(href/src/srcset 属性)与 CSS(url())中的根路径引用改写为 `/preview/<op-id>/…`,使页面与依赖资源自包含在该 op 命名空间内;动态拼接路径(ADR-0010 四入口 JS)以反例 4 的双预览验收兜底,发现即补改写清单。
- **导航首版收敛(审计触发的收敛定案:原「保留站内链接导航」承诺不成立)**:审计真实点击探针站内链接后服务端记录 auth=none/401——opaque origin 的子文档导航请求不带会话,「能在预览里浏览整站」从未实现。按最小写作需求收敛,不再承诺站内跨页导航:
  - 预览只用于**当前文章的静态校对**;返回编辑、重新打开预览由外层工作台承担;
  - 构建后改写阶段把**站内与外部 `<a>` 一律去 href**,保留链接文字与目标信息(`data-wb-target` 属性承载原 href,校对时可查),样式保持链接外观;
  - **页内锚点(`#…`)保留**——同文档滚动,不产生网络请求、不离开预览文档,属校对需求;
  - 不为导航问题扩大资源 token 到 HTML 或管理 API(见资源鉴权两层:HTML 只认会话,API 只认会话+三层校验);
  - 验收=**实际点击**改写后的链接并确认「页面 url 不变+服务端零新请求」,不以 DOM 里 href 字符串检查代替(探针 v2.1 组 N)。
- 资源归属:HTML/CSS/JS/字体/图片/3d 资产=预览产物内文件,经 `/preview/<id>/` 映射,全部会话后;外部资源(绝对 http 引用)=浏览器直连,不经工作台;管理 API(/api/*)=不属于预览命名空间,前缀改写永不指向它。
- **存活(单一规则,不再并行承诺「删旧」与「24h 有效」)**:预览固定 **24h 过期**;同一草稿生成新预览**不删**旧预览;`previews/` 总量超上限(首版 10 份)时从最旧清理。打开中的预览在 24h 内且未被总量清理时始终可访问;过期/被清理的预览 URL 返回 410+「重新生成预览」。
- **删除 worktree 不影响预览**:worktree 只是构建脚手架,构建完拷贝产物即删;预览资源全部来自独立副本。
- 预览页带明显「草稿预览」横幅,且响应头 `X-Robots-Tag: noindex`(noindex 防索引,不是访问控制;访问控制=会话中间件)。

**活动内容策略(勘误轮定案:静态校对预览,响应头 CSP sandbox 且无 allow-scripts)**:

- **隔离机制=HTTP 响应头 `Content-Security-Policy: sandbox`(无 `allow-scripts`)**:工作台返回预览 HTML 时统一注入。CSP `sandbox` 指令作用于**文档自身**、**与加载方式无关**——管理页内嵌 iframe、地址栏直接打开、独立新标签页打开,文档一律进入 opaque origin 且**脚本一律不执行**(作者活动内容与公开站增强脚本同等对待;零执行比「可执行但不可达」更硬,也不再依赖「脚本会运行」这一前提);管理页内嵌另叠加 `<iframe sandbox="">` 属性作纵深,但**不是唯一层**。
- opaque origin+静态的效果(**一套承诺,不再并存「全部增强保真」与「隔离后降级」两种说法**):零脚本执行——管理会话不可达、无表单提交、无顶层导航、无跨页导航(链接去 href 保留文字与目标)、无 localStorage/cookie 读写;保留=真实排版与字体(经上节资源 token 加载)、明暗主题 CSS、文章配图、链接文字与目标信息、页内锚点滚动;不执行=作者活动脚本、公开站 3D/增强交互、站内/外部跨页导航。预览横幅如实标注「静态校对预览:不执行脚本、不可导航」。
- **首版允许的作者内容与保留体验(目标=可靠校对文章,不为复现全部装饰效果而放宽隔离)**:放行=普通 Markdown 排版(标题/段落/引用/列表/代码块)、链接、文章配图;保留=真实排版与字体、明暗主题的 CSS 部分、链接文字与目标信息、页内锚点。不执行=全部脚本(作者活动内容与公开站增强交互,含 3D)与全部跨页导航——没有「可执行但降级」「可点击但 404」的中间态,横幅如实标注。
- **管理 API 校验独立成立,不以「没有 CORS」「opaque origin」一句话替代**:①身份=每请求校验会话 cookie(服务端会话表);②CSRF=修改类 API 校验 Origin/Referer+X-Requested-With 预检(§3);③未授权一律 401/403,与调用方是否在预览上下文无关。CSP/opaque 是纵深第一层,API 侧校验是最后一层,任一层单独失效不失守。
- 草稿原始 HTML 中的 `<script>`/事件属性在预览中**不执行**(CSP 无 allow-scripts);管理不可达由「零执行+API 侧独立校验」两层共同保证;**公开站不受本策略影响**——公开产物仍按 ADR-0010 白名单,工作台发布与作者手工 push 同一构建链路、同一公开规则(见 §10)。

| 入口 | 生效机制 |

| 2 | 提交已生成 | repo.wt 内 commit 已创建,push github 未返回 | 发布中 |
| 3 | 备份已接收 | push github 成功 | 发布中 |
| 4 | 部署端已接收 | push deploy 成功(返回成功≠已构建上线) | 发布中 |
| 5 | 确认上线 | **内容身份核对通过**(见本节末小节):当前线上目标路径内容==本操作内容(发布)/不存在(撤下) | 已上线 |
| 6 | 明确失败 | push 被拒/hook 非 ff 拒绝/构建失败等有明确失败信号 | 发布失败 |
| 7 | 暂未确认 | 180s 内未确认,**不判失败** | 未确认(后台持续轮询,可手动重查) |

**操作持久化、幂等与重启恢复(定点轮 B4 修订)**:每次发布/撤下的 operation **先落盘骨架再动 git**(不只存内存):`{id: UUID, idem_key, kind: publish|withdraw, slug, draft_rev, commit_sha: null, created/pushed_backup/pushed_deploy/confirmed/failed 时间戳, 终态}`。落盘时序与两个恢复窗口:

1. **先落骨架**:创建 operation(id+客户端幂等键落盘,commit_sha=null)→ 检出 `op/<op-id>` 分支(分支名即操作身份锚,先于 commit 存在)→ commit → **落盘 commit_sha** → 双跳 push。
2. **窗口①:commit 已产生、commit_sha 未落盘中断**——恢复按 `op/<op-id>` 分支 HEAD 读回 SHA 补记,**不生成第二个同义提交**;分支 HEAD 仍等于基准 main(提交未发生)→该操作按未提交重做。
3. **窗口②:创建操作的首次响应丢失**(客户端未拿到 operation id)——创建请求携带**客户端生成的幂等键**,重试同键→服务端发现既有 operation 返回同一记录,不重复创建。前端按钮禁用只是 UI 辅助,防重复不依赖它。
4. 已有进行中的发布/撤下时,新的发布/撤下请求直接 409「上一次操作还在进行中」(单作者串行),不做操作排队。

进程重启后对每条未终态操作按 `commit_sha` 重放判定:SHA 已在 github main→态 3;已在 deploy main→态 4;均无→回到对应态恢复路径(§2.1 表);**确认类判定一律走内容身份核对**(本节末小节),不只看 release.txt 是否等于本 SHA。

**列表「已上线」的判定口径**:不以「git 仓库里存在该文章 md」为准(那只证明提交过,不证明上线过);**URL 返回 200 也不能单独证明版本正确**(旧版本的文章页同样 200)。判定=内容身份核对(本节末小节)驱动的操作终态;GET 文章 URL 仅作存在性辅助信号(撤下终验=404)。

流程:发布按钮(二次确认:显示标题/slug/是否含撤下项)→ 创建 operation(幂等键+骨架落盘)→ repo.wt fetch+ff 校验(§6)→ 草稿转正式 md(`draft` 字段省缺=false)→ 检出 `op/<op-id>` → commit(署名 `nanmu <workbench>`,message `post(site): 发布〈标题〉`)→ 落盘 commit_sha → push github main(态 2→3)→ push deploy main(态 3→4)→ 后台轮询+内容身份核对(180s 口径)→ 核对通过转态 5,草稿移入「已发布」;明确失败信号转态 6 并保留草稿;仅超时转态 7。

**五中断场景推演(态 7 或进程中断的恢复路径)**:

| 中断点 | 现场证据 | 恢复动作 |
|---|---|---|
| 推送 github 前 | commit 只在 `op/<op-id>` 分支 | 重试 push 同一 commit(不重做) |
| github 已接收,deploy 未接收 | github main == SHA,deploy main != SHA | 重试 push deploy 同一 SHA(不重做 commit) |
| deploy 已接收,确认前进程中断 | deploy main == SHA,release.txt 未知 | 不重复 push,按重放逻辑轮询+内容身份核对 |
| 实际已上线但未补记确认 | release.txt 对应版本含本操作内容 | 内容身份核对通过后补记「已上线」 |
| 后续版本已上线 | release.txt 为更新 SHA,祖先链含本 SHA | 按内容身份核对:内容仍一致→「生效中(被后续版本包含)」;已不一致→「已被后续变更替代」(见下节) |

**上线判定的内容身份核对(定点轮 B4:祖先链只是提交关系证据,不证明内容在线)**:对每条操作区分三个问题——

- **本操作目标内容当前是否在线**:读当前 release.txt 的 SHA(release SHA),在其 git 树中查目标路径:发布/修改类=该路径 blob 的内容 hash **等于本操作写入的内容**才确认生效;撤下类=该路径**不存在**才确认生效(GET 文章 URL 404 作辅助终验)。
- **是否有证据证明本操作版本曾上线(收口轮:撤回「releases/<SHA>/ 目录存在=曾上线」)**:按 [deploy.sh](../../../deploy/deploy.sh) 实际顺序推演——构建与自校验完成后 `mv -T` 把产物放进 `releases/<SHA>/`(L28-38),**然后才**符号链接原子切换 `current`(L41-42)。在 L38 与 L41 之间中断:release 目录完整存在(`.complete`+`release.txt` 都对),但 current 从未指向它、该版本从未对外服务。因此 releases 目录只证明**产物已构建**,不证明曾上线。四态区分:
  1. **构建完成**(仅产物证据):`releases/<SHA>/` 存在或 deploy main 含该 SHA——显示「已构建」,不显示「曾上线」;
  2. **当前上线**:内容身份核对通过(当前 release SHA 树中目标路径内容==本操作内容);
  3. **曾确认上线**(唯一证据=工作台自己的确认记录):operation 落盘的 `confirmed` 时间戳+当时核对的 release SHA 与内容 hash——记录可支撑所显示的结论,缺记录即不显示;
  4. **历史无法确认**:无 `confirmed` 记录(如进程中断丢失、记录窗口外)→保守显示「未知」,不用 releases 目录倒推,不为此改 hook、不新增审计平台。
  当前内容身份核对同时保留:后续版本改变或撤下该内容时,早期 operation 不再显示为「当前上线」,改「已被后续变更替代」(见下一节)。
- **被后续变更替代**:本操作 SHA 在当前 release SHA 的祖先链、但目标路径当前内容与本操作不一致(被改写/重新发布/再次撤下)→显示「已被后续变更替代」,不声称本次内容在线。

**B4 反例验收(四条)**:

| 反例 | 预期 |
|---|---|
| 1. A 修改文章后 B 又改同篇,线上是 B | 当前 blob==B 的内容≠A 的→A 显示「已被后续变更替代」,仅 B 为「已上线」 |
| 2. A 发布后被 B 撤回 | 祖先链含 A 不判 A 在线;A=「已被后续变更替代」,B 以 URL 404 终验 |
| 3. commit 后、commit_sha 落盘前中断 | 恢复读 `op/<op-id>` 分支 HEAD 补记同一 SHA,不产生第二个同义提交 |
| 4. 首次创建响应丢失后重试 | 同幂等键返回同一 operation(同 id 同分支),不重复创建操作与提交 |

### 4.5 撤下
- 与发布同链路:工作台 `git rm` 该文章 md → commit(`post(site): 撤下〈标题〉`)→ push(同上状态机)。
- 撤下确认页明示影响面(从批次 C 撤稿经验固化):正文 URL 将 404、列表/首页/RSS/3D 纸面不再出现;**回滚到含该文的旧 release 会重新公开它**(若该 release 仍在保留窗口)。
- 撤下不改写 Git 历史(与既有纪律一致);旧文在 git 历史中保留。

## 5. 草稿:存哪、谁能读、如何不误进公开页

- **存储**:工作台私有目录 `/opt/nanmu-workbench/drafts/`(一草稿一目录,内为**单记录文件** `<slug>/draft.json`(正文+元数据+rev 同文件)+兜底 `draft.prev.json`,与 §4.2 保存契约一致;不再使用 meta.json/body.md 分体)。**不在 git 仓库内、不在 site 构建源内、不被 Caddy 服务**。
- **谁能读**:仅通过 §3 认证的作者会话;草稿 API 全部挂在会话中间件后,无公开路由。
- **防误公开三道闸**:
  1. 物理隔离:草稿目录与发布仓库分离;公开构建(`astro build`)只读 `site/src/content/posts/`,草稿不在其内——构建器不知道草稿存在。
  2. 显式转换:草稿→公开文章必须经「发布」动作(生成 md + commit + push),不存在自动收录路径;frontmatter `draft:true` 字段保留为纵深防御(误放源目录时构建期仍过滤,与既有 smoke「草稿泄漏」检查双层兜底)。
  3. 输出侧校验:hook 构建后的 smoke(既有)断言必需产物与草稿不泄漏;工作台发布后自行 GET 文章 URL 确认 200(或撤下后 404)作为终验。
- 草稿备份:纳入服务器每日备份(与 engine SQLite 同批;具体策略实施时定)。

## 6. 与 Git 手工编辑并发:防覆盖

- 工作台在服务器持有**裸克隆** `repo.git`(自 deploy 即 `/opt/git/nanmu-blog.git` 克隆,§2.1);每次发布/撤下前:
  1. `git fetch deploy` 更新引用(deploy=发布真相源与操作基准);`git fetch github` 供 §2.1 两端一致性核对(**不写「只读 deploy、不核对 GitHub」**——两端不一致是既有常态,核对规则见 §2.1);
  2. 基于最新 main 创建短期分支做提交;
  3. push 前检查目标 main 未前进(即推送为 fast-forward)。**非 ff=并发编辑发生**(典型:作者同时在开发机 push),工作台拒绝发布并提示「远端有新提交,已回到编辑,请重新预览/发布」,**绝不 force push**(与既有部署纪律一致)。
- 手工编辑侧无需感知工作台:git 是唯一真相源,两边最终以 bare repo 收敛。

## 7. 故障与降级

| 故障 | 影响 | 行为 |
|---|---|---|
| 工作台进程崩溃/停机 | 仅写作能力不可用 | 公开站照常(Caddy→静态文件,不经工作台);systemd 自动重启;草稿在磁盘不丢 |
| 发布中 hook 构建失败 | 发布失败,线上仍是旧版 | 原子切版保证;hook 侧**明确失败信号**→「发布失败」提示人工查看(不自动回滚、不自动重试);仅 180s 无确认→「暂未确认」持续轮询(§4.4),不与失败混同 |
| 预览构建失败 | 预览不可用 | 返回构建错误原文(作者可修);不影响任何已发布内容 |
| 口令遗忘 | 无法登录 | 服务器重置 env(手册化操作),不设找回流程 |

## 8. 对既有约束的调整(需新 ADR,实施第 1 步)

- **ADR-0002(静态站无后台)**:原约束语义=「公开站不给读者任何动态面、git 即 CMS」。调整=精确分面:
  - 公开站(读者侧)**不变**:仍无后台、无数据库、无会话,客户端 JS 白名单(ADR-0010)不变——工作台页面不混入公开站构建产物。
  - 新增**作者私有工作台**:独立进程/端口/认证/存储,不触碰公开站静态性质;它发布内容的唯一出口是 git commit+push(与作者手工操作完全同权同路)。
  - 实施时立 ADR-0011 记录此修订;ADR-0002 正文加一行指向。(2026-10-21 已完成:[ADR-0011](../../decisions/0011-workbench-author-facet.md);spec 三处「无后台」表述与 AGENTS 入口已同步加注。)
- **铁律不变清单**:博客本体不为 AI 加复杂度(工作台属博客本体自身的作者工具,不涉 AI);engine 隔离(铁律 3)不涉;topic-digest 只读(铁律 4)不涉;付费红线(铁律 5)不涉;页面不调模型(铁律 6)不涉;AI 标注(铁律 7)不涉;文档随代码走(铁律 8)照常。
- **部署边界新增**:工作台是新的服务器组件,其 systemd/Caddy 反代/env 属新增配置,实施时按部署手册流程走授权;不改既有 hook、不改 Caddy 主站配置文件既有段(只加子域反代段)。

## 10. 安全清单(实施对照)

- 口令仅 env 慢哈希;登录限速;会话 cookie 三标记;失败日志不含口令。
- 草稿/预览/发布 API 全部会话后;预览 noindex;无公开枚举接口。
- git:deploy 为服务器本地路径,无需远程凭据;github 推送使用 §2.1 的服务器端 deploy key,凭据只存服务器标准位置(`~/.ssh/` 或 env),不进工作台代码/配置/日志;bare repo 权限沿用部署手册。
- 不上传任意文件(仅 md 文本字段)。Markdown 渲染发生在构建期、与公开站同一渲染器——**但「渲染器相同」只降低差异风险,不构成「无新增注入面」的结论**(定点轮 B4 删去原句):信任源=作者本人(与手工 push 等同,不新增信任对象)。预览侧活动内容的处理**不在公开链路做清理**,由 §4.3 定案的静态校对预览(CSP sandbox 无 allow-scripts,脚本零执行+管理 API 独立校验)承载;公开站产物仍按 ADR-0010 白名单,不受预览策略影响。
